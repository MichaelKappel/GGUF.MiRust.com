# Package Security

The TinyRustLM NuGet SDK is a protected public boundary, not a source distribution of the full product.

## Included

- `.slm` validation, inspection, and safe loading.
- Runtime harness operations for local `.slm` execution.
- Metadata-only P2P manifest, share metadata, announcement, announcement-catalog inspection, import plan, share-kit, local assembly, and local receipt-inspection workflows.
- .NET wrappers, tests, samples, and native assets.

## Excluded

- `.slm` authoring internals.
- Model conversion and quantization authoring tools.
- Premium weights, adapter authoring, adapter auto-assembly, selector generation, offline breeding, lineage promotion, eval/provenance authoring, model-ranking logic, premium optimizers, encryption key handling, telemetry backends, license server internals, and server-assisted commercial features.

## Native Boundary

The native library returns JSON envelopes and owns runtime handles internally. Callers receive only validated reports, generated text, diagnostics, and metadata workflow outputs. Native strings must be freed through the exported `tinyrustlm_string_free` function; the .NET wrapper handles this automatically.

The .NET runtime wrapper validates managed generation options before crossing the native boundary, and the native public runtime SDK repeats the same validation before runtime mutation for direct ABI callers. Token counts, top-k candidate caps, and sampling probabilities must stay within the public fixed-buffer sampler contract. Invalid .NET values fail as managed argument errors; invalid direct native values fail with an `invalid_generation_options` JSON envelope rather than being widened, wrapped, or allowed to reach sampler calls.

The .NET wrapper also rejects embedded NUL characters in every managed string before P/Invoke. This keeps file paths, prompts, JSON handoff documents, and share-kit request fields from being silently truncated by native C-string parsing.

The .NET P2P wrapper mirrors Rust-side JSON byte budgets before native calls. Manifest handoffs over 1 MiB, announcement handoffs over 256 KiB, local import receipt handoffs over 256 KiB, and announcement catalog handoffs over 4 MiB fail as managed argument errors before native C-string allocation or Rust parsing.

The bridge preserves empty managed strings as empty native strings rather than null pointers, so empty prompts and empty-but-present handoff values cannot be confused with omitted optional arguments.

The .NET P2P wrapper validates the outer share-kit request shape before native JSON serialization. Missing `ModelPath` / `OutputDir` and `PieceSize` values outside 1 KiB through 16 MiB fail as managed argument errors before the request can reach the native bridge.

## Release Checks

`eng/verify-package.ps1` or `eng/verify-package.sh` must pass before publishing. It verifies Rust formatting/tests, .NET build/tests, NuGet packing, required native assets, package contents that must not include private authoring crates, source files, debug symbols, generated build-output directories, or local absolute paths, and a clean temporary consumer app that installs the produced packages and uses only the public `.slm`, runtime, P2P metadata, announcement JSON handoff, catalog application and inspection, local assembly, and receipt-inspection APIs.

For local development, required native assets default to the current machine RID. The official release workflow builds and downloads native bridge artifacts for `win-x64`, `linux-x64`, `osx-x64`, and `osx-arm64`, then runs `eng/verify-package.ps1 -RequiredNativeRids win-x64,linux-x64,osx-x64,osx-arm64` before publishing.

Both verifier entrypoints write `artifacts/reports/tinyrustlm-nuget-package-audit.json`, a machine-readable audit record with the expected source-versioned package names, missing/unexpected package entries, package identity checks, package hashes, package sizes, package ZIP entry names, allowed package entry patterns, unexpected package content entries, required NuGet metadata, declared package-file entries, package documentation entries, expected package documentation source hashes, packaged documentation hashes, XML documentation entries, expected dependency entries, dependency metadata, native RID coverage, allowed native entries, required RID gaps, native placement evidence, private-surface scan results, source/debug-symbol/generated-output leakage counts, and local absolute path match counts. The audit fails if the package folder does not contain exactly `TinyRustLM.Abstractions`, `TinyRustLM.Core`, and `TinyRustLM.P2P` at the source-declared version, or if any package's nuspec `id` / `version` differs from its protected filename and source version. The audit fails if any package entry falls outside the narrow public allow-list: NuGet metadata, nuspec, README/license, package-specific public docs, `lib/net8.0` DLL/XML outputs, and approved Core native runtime assets. The audit fails if declared docs are missing or if packaged README/license/package docs do not byte-match the current `docs/nuget` sources. The audit fails if package dependencies drift away from the public graph: `TinyRustLM.Abstractions` has no package dependencies, `TinyRustLM.Core` depends only on same-version `TinyRustLM.Abstractions`, and `TinyRustLM.P2P` depends only on same-version `TinyRustLM.Abstractions` and `TinyRustLM.Core`. The dependency audit also requires protected package references to retain `exclude=Build,Analyzers` metadata. The audit also fails if native runtime entries appear outside `TinyRustLM.Core`, or if `TinyRustLM.Core` carries native files outside the allowed RID/native filename set; `TinyRustLM.Abstractions` and `TinyRustLM.P2P` stay managed metadata/API packages. CI and release workflows upload this report as a build artifact.

`eng/publish-nuget.ps1 -DryRun -SkipVerification` lists the exact packages that would be pushed after package verification. Real publication requires `NUGET_API_KEY` or `-ApiKey` and validates that exactly the three protected SDK packages are present before pushing. For NuGet.org Trusted Publishing, the release workflow obtains a short-lived NuGet.org key with `NuGet/login@v1` and passes it through the same `-ApiKey` path; private feeds continue to use scoped API keys. Stale versions, renamed package experiments, unintended extra `TinyRustLM*.nupkg` files, missing package-audit reports, or packages whose SHA-256/byte counts differ from `tinyrustlm-nuget-package-audit.json` fail closed before any push. The command writes `artifacts/reports/tinyrustlm-nuget-publish-plan.json` with the exact package names, hashes, sizes, package source, target feed, package-audit report hash, audit match status, dry-run/push status, and `secret_material_included=false`; release workflows validate and upload this report as publish evidence whenever the report exists. If `dotnet nuget push` fails during an authenticated publish, the scripts overwrite the report with status `push_failed` and a redacted `publish_error` so partial attempts cannot be mistaken for publish-ready evidence.

`eng/audit-nuget-release-readiness.ps1` and `eng/audit-nuget-release-readiness.sh` are the no-push release-readiness gate. They refresh the dry-run publish plan, run local package-folder feed-current and feed-hash checks, query the target feed, verify target-feed package bytes when the declared version is already present, and write `artifacts/reports/tinyrustlm-nuget-release-readiness.json`. Before each sub-step, the expected subreport path is removed; the readiness report then records `report_written` for that step. This prevents stale feed-current, feed-hash, or publish-plan JSON from being reused when a step fails before writing fresh evidence. The report records `auth_mode`, `api_key_present`, `trusted_publishing_requested`, and `trusted_publishing_supported` only as non-secret booleans/labels and keeps `secret_material_included=false`; `blocked_trusted_publishing_unsupported` prevents accidental private-feed pushes through NuGet.org-only OIDC mode. The official release workflow runs the PowerShell audit with `-FailOnBlocked` before `dotnet nuget push`, validates and uploads the readiness report when it exists, skips the push step when readiness is already `published_current`, and still runs the mandatory feed-current/feed-hash gates.

For NuGet.org releases, prefer `auth_mode=trusted_publishing` after a NuGet.org trusted publishing policy has been configured for repository, workflow file `release-nuget.yml`, and environment `nuget-release`. The workflow grants `id-token: write`, logs in through `NuGet/login@v1`, and never stores the temporary push key in release evidence. Use `auth_mode=api_key` for private feeds or for legacy scoped NuGet.org keys.

`eng/verify-feed.ps1` is the clean consumer post-publish smoke. It installs the protected SDK packages from a configured feed into an isolated clean consumer app, then repeats `.slm`, runtime, and P2P metadata workflow smoke coverage without using the local package artifact directory. It writes `artifacts/reports/tinyrustlm-nuget-feed-smoke.json`. The Unix wrapper records dependency failures, such as a missing `dotnet` CLI, in the same report schema. In the official release workflow this smoke is optional through `verify_after_publish`; feed-current and feed-hash verification are mandatory after every publish.

`eng/verify-feed-current.ps1` is the feed freshness gate. It writes `artifacts/reports/tinyrustlm-nuget-feed-current.json` and fails when any protected package is missing the source-declared version or when the feed reports a newer version than the source tree. This keeps the NuGet distribution aligned with `dotnet/Directory.Build.props`.

`eng/verify-feed-package-hashes.ps1` is the feed artifact-integrity gate. It reads `artifacts/reports/tinyrustlm-nuget-publish-plan.json`, downloads or reads each protected package from a NuGet v3 feed or local package folder, compares SHA-256 values and byte counts with the audited publish plan, and writes `artifacts/reports/tinyrustlm-nuget-feed-hashes.json`. The official release workflow runs both feed-current and feed-hash gates after publishing and retries briefly to tolerate feed indexing delay before failing the release.

`.github/workflows/nuget-feed-monitor.yml` is the ongoing feed monitor. It runs the same freshness gate on demand and can run daily once `TINYRUSTLM_NUGET_MONITOR_ENABLED=true` is configured for the repository. The monitor does not use package-push secrets. It uploads the feed-current report by default, when `TINYRUSTLM_NUGET_MONITOR_VERIFY_CONSUMER=true` it also uploads the clean consumer feed-smoke report, and when `TINYRUSTLM_NUGET_MONITOR_VERIFY_HASHES=true` plus `TINYRUSTLM_NUGET_MONITOR_PUBLISH_PLAN_REPORT=<path>` are configured it also uploads feed package-byte hash evidence.
